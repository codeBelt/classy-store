# Stage 3: behaviour that tests pin and the docs do not promise

Stage 3 step 5 of `REVIEW_PLAN.md`, for the decision document. No spikes, no
code changed.

## Summary

- **547 tests** in the 44 files stage 1 added, plus the extended fuzz test,
  were read by name, with every `// FINDING:` comment mapped to its tests.
  The table below has one row per behaviour or per tight group: 250 rows.
- **56 rows are already promised** by `website/content/docs/`, mostly by
  `API_REFERENCE.md` and the tutorial, and need no label. `ARCHITECTURE.md` says of itself
  that it is "internal design documentation for contributors and
  maintainers", so a sentence found only there is marked **ARCH** and counts
  as a description, not a promise to users.
- **47 rows are defects** by stage 1 finding number, or a first-wave "fixes"
  test. They get no label.
- **147 rows get a label**, many split as "G / U" (one part guaranteed, one
  unspecified). **For these I recommend three rules** that settle most rows at once. The
  decision document can adopt the rules and keep the table as the evidence:
  1. **Subscribers.** Guaranteed: the order on one node is the order of
     `subscribe()`; a subscriber hears only writes made after `subscribe()`
     returned and none after its unsubscribe function returned; a throwing
     subscriber leaves the write applied, the other subscribers called and
     itself subscribed. Unspecified: the order across nodes, owners and stores,
     how re-entrant writes nest, which microtask a round runs in, and where a
     subscriber's error is reported.
  2. **Getters.** Guaranteed: a getter is lazy, returns the same result while
     nothing it read through `this` changed, and is correct after anything it
     read changed. Unspecified: whether it re-runs more often than that (a
     write under an object it read, a whole-array dependency, an inner
     getter's equal result), whether errors are cached, and the text of the
     cycle error.
  3. **Reflection and the raw object.** Guaranteed: a store behaves like the
     object behind it for the native invariants (`TypeError` on a refused write
     in strict mode, `false` from `Reflect`, sealed and frozen semantics, key
     order, holes). Unspecified: what reflection hands out
     (`getOwnPropertyDescriptor`, `structuredClone` of a store) and anything
     reached through the raw object.
- **The first-wave "incidental" tests** are all labelled in the table: 3 from
  D1, 12 from D2, 1 from T1 strict, 4 from T3 (b), 1 from G1, 4 from G4 and 4
  from G7b, plus the 3 cycle tests that only "errors cached" fails. One
  conflict: T4's variant S1 calls the snapshot-getter write test
  incidental, G7a calls it a fix. I treat it as defect 39.
- **Docs promise things no test checks:** 9 items at the end, two of them
  checked by hand here and holding (`shallowEqual` and symbol keys, and its
  argument order).
- **One process point.** The type tests assert each entry's export list
  exactly, so they fail when an export is _added_. Adding an export is not a
  breaking change. The rule should be: the listed exports are guaranteed,
  the list may grow in a minor release, and the test is a change detector.

## Documented and not checked by a test

Found by searching the tests for each promise in `API_REFERENCE.md`, the
tutorials and the guides. A search, not a proof: a test can check a promise
under words I did not try.

1. **`shallowEqual` ignores symbol keys** (API: "Symbol keys are not
   compared"). No test. Checked here by hand: `shallowEqual({a: 1, [s]: 1},
{a: 1, [s]: 2})` is `true`.
2. **`shallowEqual` can depend on argument order when enumerability differs**
   (API). No test. Checked by hand: `{x: 1}` against `{y: 1}` plus a
   non-enumerable `x` gives `true` one way and `false` the other.
3. **`map.set(key, value)` on an existing key keeps the stored key and its
   position** (COLL). The fuzz test models it; no named test asserts the
   position.
4. **Reading `.size` takes constant time; lookups are linear** (COLL). Cost
   only; nothing measures it.
5. **"An `async` method is a transaction up to its first `await`"** (TUT).
   `core.transactions.test.ts` has async cases; I did not confirm one asserts
   the boundary at the first `await` exactly.
6. **`dispose()` of `devtools` called again does nothing** (API). Covered by
   one line inside "disposes correctly", which asserts no extra send, not
   that the second call has no other effect.
7. **"A same-key event from another storage area can therefore update this
   store too"** (PT). The tests set `storageArea`; I found none that checks
   the cross-area case.
8. **"Each reactive object has one versioned snapshot shared across all
   paths"** (ARCH). Tested for two stores and nested proxies (I), but it is
   only in the contributor doc; if it is guaranteed it should move to the API
   page.
9. **ESM and CommonJS callers can pass stores between them** (API). Checked by
   `tests/compatibility/entrypoints.fixture.mjs`, outside the unit suite; it
   runs in CI's compatibility job only.

## Documentation that a recommendation here changes

- If rule 1 is adopted, `API_REFERENCE.md` under `subscribe()` needs three
  sentences: order on one node, the after-`subscribe()` and
  after-unsubscribe rule, and what a throwing subscriber does. The order across
  owners and stores, and where an error goes, get one sentence saying they are
  unspecified.
- If rule 2 is adopted, the "Getters" bullet of `createClassyStore` gains:
  lazy, same result while nothing read changed, may re-run more often.
- Rows marked "documented as a limit" and also a defect (findings 1, 30, 31,
  32, 57) change a documented sentence when fixed, so those fixes are
  **Before 1.0** even where the code change is small.
- The tutorial's "a frozen root's writes throw" should say "a write that
  changes a value throws".
